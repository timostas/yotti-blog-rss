# RSS import contract: Yotti

Статус документа: подтверждённые наблюдения по состоянию на 02.09.2026.

Этот документ фиксирует только фактически проверенное поведение цепочки публикации Yotti Blog:

`Markdown → GitHub → GitHub Actions → GitHub Pages RSS → импортёр Yotti → публичная статья Yotti`.

Документ не описывает предполагаемую внутреннюю реализацию импортёра и не делает выводов о полях, которые не были изолированно протестированы.

## Production RSS

- RU: `https://timostas.github.io/yotti-blog-rss/ru/rss.xml`
- EN: `https://timostas.github.io/yotti-blog-rss/en/rss.xml`

Оба URL используются как отдельные источники для соответствующих языковых потоков Yotti.

## Подтверждено

1. Production RU RSS успешно собирается и публикуется через штатный GitHub Actions workflow и GitHub Pages.
2. Новая русская RSS-запись после ручной синхронизации импортируется в Yotti.
3. Полный текст RSS-записи доходит до публичной статьи Yotti.
4. Yotti создаёт собственный публичный URL статьи, отличный от технического RSS `<link>`.
5. При повторной синхронизации одной и той же RSS-записи, когда были сохранены файл, `slug`, RSS `<link>`, `title`, `pubDate` и остальные метаданные, но изменено только тело записи, Yotti обновил существующую статью.
6. Публичный URL Yotti при таком обновлении не изменился.
7. Новая версия тела заменила предыдущую: `VERSION-2` заменила `VERSION-1`.
8. Новый контрольный маркер `RSS_CONTRACT_UPDATE_MARKER: BODY-UPDATED-2026-08-14` появился в существующей публичной статье.
9. Дубликат статьи при обновлении не был создан.
10. RU/EN-разделение сохранилось: тестовая русская статья и её контрольные маркеры отсутствовали в EN RSS.
11. При замене байтов обложки по прежнему исходному URL повторная синхронизация
    обновила время записи, но оставила ранее сохранённое изображение Yotti.
12. После публикации обложки по новому версионному URL и ещё одной синхронизации
    тело статьи обновилось, но карточка в общем списке сохранила прежний
    `coverImageUrl` в хранилище Yotti. На момент проверки запись имела
    `syncedAt: 2026-08-15T16:09:13.816+00:00`.

## Контрольный эксперимент VERSION-1 → VERSION-2

Тестовая статья была опубликована в RU RSS с постоянным техническим RSS link:

`https://timostas.github.io/yotti-blog-rss/ru/articles/rss-contract-update-test-20260814.html`

После первой ручной синхронизации Yotti создал публичную статью:

`https://yotti.net/blog/test-rss-kontrakt-proverka-obnovleniya-version-1`

В VERSION-1 на публичной странице были подтверждены маркеры:

- `RSS_CONTRACT_TEST_ID: 2026-08-14-A`
- `RSS_CONTRACT_VERSION: VERSION-1`

Затем в том же исходном Markdown-файле был изменён только body-контент теста:

- `RSS_CONTRACT_VERSION: VERSION-1` → `RSS_CONTRACT_VERSION: VERSION-2`
- добавлен `RSS_CONTRACT_UPDATE_MARKER: BODY-UPDATED-2026-08-14`

При этом намеренно не менялись:

- имя файла;
- `slug`;
- RSS `<link>`;
- `title`;
- `pubDate`;
- остальные поля YAML front matter.

После публикации VERSION-2 в production RSS и повторной ручной синхронизации Yotti:

- существующий публичный URL остался тем же;
- на той же странице появилась `VERSION-2`;
- `VERSION-1` исчезла;
- появился `BODY-UPDATED-2026-08-14`;
- второй экземпляр статьи в Yotti не появился.

## Что этот тест НЕ доказывает

Тест не позволяет определить, какое именно поле или комбинация полей используется импортёром Yotti как уникальный ключ записи. В частности, нельзя утверждать, что дедупликация или обновление выполняются именно по RSS `<link>`.

## Пока неизвестно / требует отдельного теста

- точный уникальный ключ дедупликации импортёра;
- поведение при изменении `title`;
- поведение при изменении `pubDate`;
- ручное обновление обложки существующей статьи через админку;
- изменение импортёра, которое позволит обновлять `coverImageUrl` из нового
  URL `enclosure`;
- перенос ALT и других атрибутов изображения;
- маппинг категорий и стран;
- поведение при удалении записи из RSS;
- поведение при `published: false` после предыдущего импорта;
- статусы и диагностика ошибок импорта;
- retry после ошибки;
- rollback и восстановление после некорректной публикации.

## Эксперимент rich-metadata (24.08.2026, подтверждён частично)

Для одной уже существующей RU-статьи `deleted-esim-recovery-ru` подготовлен
изолированный эксперимент. Её `slug`, RSS `<link>`, заголовок и исходный
`pubDate` сохранены: это снижает риск создания дубля по подтверждённому
сценарию обновления текста.

В запись добавлены только переносимые стандартные поля: `dc:creator`,
`dc:publisher`, `dc:date`, `dc:language`, `dc:rights`, `dcterms:modified`,
`atom:updated`, `atom:link` на EN-версию, `content:encoded` и Media RSS
(`media:content`, `media:thumbnail`, название и описание изображения). В
контент записи также добавлены видимые автор, дата публикации/обновления и
подписанные ссылки на два первоисточника.

После ручной синхронизации импортёр подтвердил перенос HTML из RSS: на
публичной странице появились видимые автор, даты и ссылки на источники.
Технические поля из RSS не были перенесены в шаблон страницы: ALT обложки
остался пустым, `article:published_time`, `article:modified_time` и
`dateModified` не появились, Twitter-метаданные остались общесайтовыми, а
item-level `atom:link` не изменил `hreflang`.

По решению владельца подтверждённые видимые блоки применяются ко всем
опубликованным RU/EN-статьям. Для каждой записи сохраняются исходные `slug`,
RSS `<link>`, заголовок и `pubDate`; дата редакционной проверки берётся из уже
существующего `reviewedAt`. Источники показываются после текста статьи, чтобы
не прерывать вступление. Неподдержанные технические поля не считаются частью
массового исправления и требуют изменения шаблона сайта.

## Практический вывод

Для обычного обновления текста уже импортированной статьи текущий подтверждённый безопасный сценарий — сохранять существующие идентифицирующие и временные поля RSS-записи и менять только содержимое статьи. В протестированном сценарии Yotti обновил существующую публикацию без изменения публичного URL и без создания дубля.

Замена обложки существующей публикации через одну только RSS-синхронизацию не
подтверждена и дважды не сработала: ни при перезаписи исходного файла, ни при
новом URL `enclosure`. Для карточки требуется ручная замена в Yotti или изменение
логики импортёра.

Это операционное правило основано только на выполненном контрольном тесте и не заменяет отдельные проверки других типов изменений.

## Публичная проверка rich HTML (02.09.2026)

После синхронизации усиленной статьи про Южный остров Новой Зеландии выполнена
проверка фактического DOM публичной страницы Yotti. Импортёр:

- полностью удалил встроенный `style` и SVG-карту;
- удалил оболочки `div`, `section`, `aside`, `details` и `summary`;
- удалил `id` у заголовков, из-за чего ссылки самодельного оглавления перестали
  вести к разделам;
- сохранил саму HTML-таблицу, но удалил оформляющую оболочку и стили, поэтому
  таблица стала плотной и плохо читаемой;
- сохранил `figure`, `img`, `figcaption`, заголовки, абзацы, ссылки, списки и
  `blockquote`; публичный шаблон Yotti оформляет эти элементы предсказуемо;
- сохранил URL, размеры и alt встроенных изображений, но удалил `loading`.

Склейки «днейот», «базыбез», «переездамежду» и «резервдля» появились не из-за
редакционного текста, а из-за примыкания продолжения к `</strong>` без пробела.
После удаления CSS скрытая визуальная граница исчезла. Такой стык теперь
проверяется автоматическим тестом.

Практический формат для маршрутных материалов:

- таблицы заменяются последовательностью смысловых `blockquote`-карточек;
- CSS и SVG не передаются в тело RSS;
- карта передаётся анимированным WebP в обычном `img` и дублируется полным
  текстовым маршрутом;
- статичный WebP указывается в `picture/source` для reduced motion, но перенос
  `picture/source` остаётся непроверенным до следующей ручной синхронизации;
- реальное воспроизведение анимации считается подтверждённым только после
  проверки публичных RU/EN-страниц Yotti.
