# RSS import contract: Yotti

Статус документа: подтверждённые наблюдения по состоянию на 14.08.2026.

Этот документ фиксирует только фактически проверенное поведение цепочки публикации Yotti Blog:

`Markdown → GitHub → GitHub Actions → GitHub Pages RSS → импортёр Yotti → публичная статья Yotti`.

Документ не описывает предполагаемую внутреннюю реализацию импортёра и не делает выводов о полях, которые не были изолированно протестированы.

## Production RSS

- RU: `https://timostas.github.io/yotti-blog-rss/ru/rss.xml`
- EN: `https://timostas.github.io/yotti-blog-rss/en/rss.xml`

Оба URL используются как отдельные источники для соответствующих языковых потоков Yotti.

## Подтверждено

1. Production RU RSS успешно собирается и публикуется через штатный GitHub Actions workflow и GitHub Pages.
2. Новая русская RSS-запись после ручной синхронизации импортируется в Yotti.
3. Полный текст RSS-записи доходит до публичной статьи Yotti.
4. Yotti создаёт собственный публичный URL статьи, отличный от технического RSS `<link>`.
5. При повторной синхронизации одной и той же RSS-записи, когда были сохранены файл, `slug`, RSS `<link>`, `title`, `pubDate` и остальные метаданные, но изменено только тело записи, Yotti обновил существующую статью.
6. Публичный URL Yotti при таком обновлении не изменился.
7. Новая версия тела заменила предыдущую: `VERSION-2` заменила `VERSION-1`.
8. Новый контрольный маркер `RSS_CONTRACT_UPDATE_MARKER: BODY-UPDATED-2026-08-14` появился в существующей публичной статье.
9. Дубликат статьи при обновлении не был создан.
10. RU/EN-разделение сохранилось: тестовая русская статья и её контрольные маркеры отсутствовали в EN RSS.
11. При замене байтов обложки по прежнему исходному URL повторная синхронизация
    обновила время записи, но оставила ранее сохранённое изображение Yotti.
    Поэтому исправленная обложка должна получать новый версионный URL.

## Контрольный эксперимент VERSION-1 → VERSION-2

Тестовая статья была опубликована в RU RSS с постоянным техническим RSS link:

`https://timostas.github.io/yotti-blog-rss/ru/articles/rss-contract-update-test-20260814.html`

После первой ручной синхронизации Yotti создал публичную статью:

`https://yotti.net/blog/test-rss-kontrakt-proverka-obnovleniya-version-1`

В VERSION-1 на публичной странице были подтверждены маркеры:

- `RSS_CONTRACT_TEST_ID: 2026-08-14-A`
- `RSS_CONTRACT_VERSION: VERSION-1`

Затем в том же исходном Markdown-файле был изменён только body-контент теста:

- `RSS_CONTRACT_VERSION: VERSION-1` → `RSS_CONTRACT_VERSION: VERSION-2`
- добавлен `RSS_CONTRACT_UPDATE_MARKER: BODY-UPDATED-2026-08-14`

При этом намеренно не менялись:

- имя файла;
- `slug`;
- RSS `<link>`;
- `title`;
- `pubDate`;
- остальные поля YAML front matter.

После публикации VERSION-2 в production RSS и повторной ручной синхронизации Yotti:

- существующий публичный URL остался тем же;
- на той же странице появилась `VERSION-2`;
- `VERSION-1` исчезла;
- появился `BODY-UPDATED-2026-08-14`;
- второй экземпляр статьи в Yotti не появился.

## Что этот тест НЕ доказывает

Тест не позволяет определить, какое именно поле или комбинация полей используется импортёром Yotti как уникальный ключ записи. В частности, нельзя утверждать, что дедупликация или обновление выполняются именно по RSS `<link>`.

## Пока неизвестно / требует отдельного теста

- точный уникальный ключ дедупликации импортёра;
- поведение при изменении `title`;
- поведение при изменении `pubDate`;
- успешное обновление изображения после изменения URL `enclosure`;
- перенос ALT и других атрибутов изображения;
- маппинг категорий и стран;
- поведение при удалении записи из RSS;
- поведение при `published: false` после предыдущего импорта;
- статусы и диагностика ошибок импорта;
- retry после ошибки;
- rollback и восстановление после некорректной публикации.

## Практический вывод

Для обычного обновления текста уже импортированной статьи текущий подтверждённый безопасный сценарий — сохранять существующие идентифицирующие и временные поля RSS-записи и менять только содержимое статьи. В протестированном сценарии Yotti обновил существующую публикацию без изменения публичного URL и без создания дубля.

Это операционное правило основано только на выполненном контрольном тесте и не заменяет отдельные проверки других типов изменений.
